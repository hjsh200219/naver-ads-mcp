`src/runtime/lock.ts`는 proper-lockfile 기반 (client, week) 단위 advisory lock이지만 v1.6에서는 **serialize-only**다. 같은 (client, week) prepare를 N건 동시 호출하면 N건 모두 성공한다. 단지 lock으로 직렬화되어 partial/torn file이 0건 보장될 뿐.

**Why:**
v1.5에는 `send_report_email` tool이 있었고 그때는 "같은 (client, week) 발송 2건 동시 호출 → 1건만 통과, 1건 lock 거절"이 의도였다 (광고주 이중 수신 방지). v1.6에서 발송 책임을 AE 메일 클라이언트로 이전하면서 send_report_email tool 자체가 삭제됐다. 남은 prepare는 multi-revision이 정상적인 AE 워크플로우이므로 lock 거절이 오히려 마찰을 만든다.

`tests/output-files.test.ts`의 "concurrent writes for same (client, week)"는 3건 모두 성공을 expect한다. `proper-lockfile` retries `{ retries: 50, factor: 1, minTimeout: 5, maxTimeout: 50 }`로 5건 동시도 ~50ms 안에 완료.

**How to apply:**

- 누군가 "prepare 동시 호출 시 1건 거절돼야 하지 않나?"라고 물으면 — v1.5 SEND 시대의 개념. v1.6 PREPARE는 직렬화만 함.
- plan v1.6 Verification #11, Phase 3 완료 기준, PRD AC #14 모두 "serialize-only"로 정정 완료.
- 만약 광고주 발송 이중 도달 방지가 요구되면 prepare 레이어가 아닌 AE 메일 클라이언트의 sent items가 source of truth (외부 책임).
