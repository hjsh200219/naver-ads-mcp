## 1. 요구사항 명세

### 사용자가 표현한 것

> ".env의 NAVER_ADS_ID, NAVER_ADS_PW를 이용해서 https://ads.naver.com에 접속하는 기능이 필요해."

### 실제로 필요한 것 (해석 후보)

| 해석           | 의미                                              | 구현 난이도 | 비고                                            |
| -------------- | ------------------------------------------------- | ----------- | ----------------------------------------------- |
| A. 인증 검증   | ID/PW로 로그인 가능 여부만 확인                   | 중          | 공식 API 없음 — 웹 자동화 필수                  |
| B. 데이터 조회 | 광고 계정의 캠페인·키워드·비용 등 데이터 가져오기 | 중~고       | **공식 Search Ad API로 가능** (단, API 키 필요) |
| C. 자동 작업   | 입찰가 조정, 캠페인 on/off, 소재 등록 등 자동화   | 고          | API로 일부, UI 전용 작업은 웹 자동화 필요       |
| D. SSO 통합    | 다른 앱에서 네이버 계정으로 로그인                | 중          | OAuth — 본 요구사항과 무관할 가능성 높음        |

**핵심 불명확 사항**: 사용자가 준 것은 **ID/PW**(웹 로그인 자격증명)이지만, 네이버 광고 데이터 접근의 **공식 경로**는 `CUSTOMER_ID` + `ACCESS_LICENSE` + `SECRET_KEY` 기반의 REST API다. 이 간극이 이번 계획의 가장 중요한 의사결정 지점이다.

**추가 불명확 사항 [R-2]**: 네이버 Search Ad API는 **검색광고(SA)만** 커버한다. Sister project `zebra-brothers-ax`(HelloMax 6개 광고주 주간 성과 리포트 AI 분석)의 컨텍스트상 대행사 계정이 GFA(성과형 디스플레이), 브랜드검색, 쇼핑검색 등 다른 광고 상품도 운용할 가능성이 높다. 사용자가 필요로 하는 광고 상품 유형이 Q5로 추가되었다.

## 2. RALPLAN-DR Summary

### Principles (원칙 5개)

| #   | 원칙                          | 근거                                                                                                          |
| --- | ----------------------------- | ------------------------------------------------------------------------------------------------------------- |
| P1  | **자격증명 안전**             | `.env` 비커밋, 로그 마스킹, 메모리 노출 최소화. 자격증명이 코드·로그·에러 메시지에 절대 평문 노출되지 않을 것 |
| P2  | **합법성·ToS 준수**           | 네이버 이용약관 위반 가능성이 있는 경로는 위험을 명시하고, 공식 API 경로를 우선                               |
| P3  | **검증 가능성 (Testability)** | 모든 핵심 로직(서명 생성, 자격증명 로딩, API 호출)에 단위·통합 테스트 작성 가능할 것                          |
| P4  | **그린필드 단순성**           | 과설계 금지. 최소 의존성, 최소 파일 구조. 동작하는 최소 버전 먼저                                             |
| P5  | **점진적 위험 (Escalation)**  | API 경로 우선 시도 → API로 불가능한 작업만 웹 자동화 검토. 웹 자동화는 최후수단                               |

### Decision Drivers (의사결정 동인 Top 3)

| #      | 동인                                                                                                         | 영향                                                                              |
| ------ | ------------------------------------------------------------------------------------------------------------ | --------------------------------------------------------------------------------- |
| **D1** | **사용 목적** — 단순 검증 / 데이터 추출 / 자동 작업                                                          | 전체 아키텍처와 접근 방식을 결정함                                                |
| **D2** | **합법 API 경로 사용 가능 여부** — Search Ad API의 `CUSTOMER_ID`/`ACCESS_LICENSE`/`SECRET_KEY` 발급 가능한가 | 가능하면 Option A, 불가하면 Option B로 갈림                                       |
| **D3** | **광고 상품 유형** — 검색광고(SA)만 / GFA 포함 / 브랜드검색·쇼핑검색 포함 [R-2]                              | Option A(Search Ad API) 커버리지 범위를 결정. SA 외 상품 필요 시 Hybrid 경로 검토 |

### Viable Options

#### Option A: Naver Search Ad API (공식 REST API) — **권장**

네이버 검색광고 API (https://naver.github.io/searchad-apidoc/) 사용.  
인증: `CUSTOMER_ID` + `ACCESS_LICENSE` + `SECRET_KEY`로 HMAC-SHA256 서명 헤더 생성.

| 항목        | 내용                                                                                                                                         |
| ----------- | -------------------------------------------------------------------------------------------------------------------------------------------- |
| **장점**    | 공식 지원·문서화, 안정적, ToS 100% 준수, HMAC 서명 → 자격증명 평문 전송 없음, 무료, Rate limit 관대                                          |
| **단점**    | 현재 `.env`의 ID/PW가 아닌 **API 키 3종 재발급 필요** (사용자 행동 요구), **검색광고(SA)만 커버** — GFA·브랜드검색·쇼핑검색 데이터 접근 불가 |
| **적합**    | 검색광고 데이터 조회 (캠페인·키워드·보고서), 계정 정보, 입찰 자동화                                                                          |
| **필요 키** | `NAVER_ADS_CUSTOMER_ID`, `NAVER_ADS_ACCESS_LICENSE`, `NAVER_ADS_SECRET_KEY`                                                                  |

#### Option B: Playwright 웹 로그인 자동화

Playwright로 `https://nid.naver.com/nidlogin.login` 접속 → ID/PW 입력 → `ads.naver.com` 리디렉션.

| 항목     | 내용                                                                                                                                                                                                                                             |
| -------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| **장점** | 현재 `.env`의 ID/PW 그대로 사용 가능, UI에서 가능한 모든 작업 수행 가능, 광고 상품 유형 무관하게 전체 데이터 접근                                                                                                                                |
| **단점** | **ToS 회색지대** — 자동 로그인 시도 자체가 약관 위반 소지, CAPTCHA·신규기기 SMS 인증·봇 탐지로 **빈번한 실패**, 유지보수 부담 매우 큼 (네이버 UI 변경 시 깨짐), 자격증명 평문 사용 → 메모리·스크린샷 노출 위험, 헤드리스 탐지 우회는 윤리적 문제 |
| **적합** | API에서 지원하지 않는 UI 전용 작업이 **반드시** 필요할 때만                                                                                                                                                                                      |

#### Option C: Naver Commerce/Login OAuth — **배제**

| 항목          | 내용                                                                                                                                                                                              |
| ------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **배제 사유** | "내 앱에 네이버 사용자가 로그인"하는 시나리오. 현재 요구사항은 "내 광고 계정에 프로그래밍적으로 접근"이므로 **용도 불일치**. OAuth 토큰으로 `ads.naver.com` 데이터에 접근하는 API는 존재하지 않음 |

#### Option Hybrid: SA API + Web 자동화 (Q5 분기) [R-2]

| 항목     | 내용                                                                                         |
| -------- | -------------------------------------------------------------------------------------------- |
| **조건** | Q5에서 검색광고 + GFA/브랜드검색 등 복수 광고 상품 데이터가 필요한 경우                      |
| **구조** | 검색광고 데이터 → Option A(API)로 처리, GFA 등 API 미지원 상품 → Option B(Web 자동화)로 보충 |
| **장점** | 커버리지 최대화, SA 영역에서는 ToS 완전 준수                                                 |
| **단점** | 두 인증 경로 유지 부담, Option B 영역의 모든 단점 계승                                       |
| **적합** | SA만으로는 부족하고 GFA 데이터가 반드시 필요한 경우에 한정                                   |

### 확장 테스트 계획 (Deliberate Mode) [R-4]

| 계층              | 테스트 항목         | 상세                                                                                                                            | 비고                                       |
| ----------------- | ------------------- | ------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------ |
| **Unit**          | 자격증명 로더       | `.env` 로딩, 필수 키 누락 시 에러 (값 미노출), 마스킹 함수 정확성                                                               |                                            |
| **Unit**          | HMAC 서명 생성      | **fixture-capture 절차**: 실 API 호출 1회 → request headers 기록 → 픽스처 저장 → 동일 입력에 대해 결정론적 서명 재현 검증 [R-4] | 네이버 공식 문서에 HMAC test vector 미제공 |
| **Unit**          | API 클라이언트      | 요청 헤더 구성, 타임스탬프(epoch ms) 형식, Base URL 조합, 재시도 로직                                                           |                                            |
| **Unit**          | 429/5xx 에러 핸들링 | `Retry-After` 존중, exponential backoff, partial failure 처리                                                                   | [R-7]                                      |
| **Integration**   | 실서버 dry-run      | 인증 완료 후 `/ncc/bizmoney` 또는 `/ncc/campaigns` GET 1건 → 200 응답 확인                                                      | `credentials-required` 마커 적용 [R-4]     |
| **E2E**           | Happy path          | 인증 → 캠페인 목록 조회 → 결과 출력의 전체 흐름                                                                                 | `credentials-required` 마커 적용           |
| **E2E**           | 에러 path           | 잘못된 키 → 명확한 에러 메시지 (키값 미노출)                                                                                    |                                            |
| **Observability** | 로그 마스킹         | 모든 로그 레벨에서 `CUSTOMER_ID`, `ACCESS_LICENSE`, `SECRET_KEY` 패턴이 출력되지 않음을 검증                                    |                                            |
| **Observability** | 실패 기록           | 재시도 횟수, HTTP 상태 코드, 응답 시간 기록 (자격증명 제외)                                                                     |                                            |
| **보안 회귀**     | `.gitignore` 검증   | `.env`가 `git ls-files`에 나타나지 않음을 테스트에서 확인. **전제: git repo 초기화 완료 (Step-0)** [R-4]                        |                                            |
| **보안 회귀**     | 로그 스캔           | stdout/stderr 캡처 후 `NAVER_ADS_*` 값 정규식 매칭 → 0건 확인                                                                   |                                            |

**CI 전략 [R-4]**: `credentials-required` 테스트 마커 도입. CI 환경에서는 해당 마커가 붙은 테스트를 skip하고, 로컬 개발 환경 또는 staging에서만 실행한다. `vitest`의 `describe.skipIf(!process.env.NAVER_ADS_SECRET_KEY)` 패턴 또는 커스텀 마커로 구현.

### 핵심 모듈 설명

**`src/naver-ads/config.ts`** [R-5] [R-6]

- `dotenv`로 `.env` 로드
- `NAVER_ADS_CUSTOMER_ID`, `NAVER_ADS_ACCESS_LICENSE`, `NAVER_ADS_SECRET_KEY` 필수 검증
- 누락 시: 에러 메시지에 **키 이름만** 표시 (값은 절대 미포함)
- 마스킹 유틸 함수: `maskSecret(value)` → `"abc...xyz"` (처음 3자·끝 3자만)
- **Credential loader interface 추상화** [R-5]: `ICredentialLoader` 인터페이스를 정의하고, 현재는 `EnvCredentialLoader`(dotenv 기반) 구현만 제공. 향후 Vercel env, GitHub Actions OIDC, 1Password CLI 등으로 swap 가능한 확장 포인트.
- **다중 CUSTOMER_ID 확장 path** [R-6]: 현재는 단일 `NAVER_ADS_CUSTOMER_ID` 값을 처리. 대행사 계정이 복수 하위 계정을 관리하는 경우를 대비하여, config 타입을 향후 `Record<string, Credentials>` 맵으로 확장 가능하도록 설계. 현재 MVP에서는 단일 값 + 확장 path 주석만 남긴다.

**`src/naver-ads/client.ts`** [R-3]

HMAC-SHA256 서명 기반 네이버 Search Ad API 클라이언트.

**HMAC 서명 상세 스펙** (참조: https://naver.github.io/searchad-apidoc/#/guides) [R-3]:

| 항목                     | 스펙                                                                                                                                                                                                  |
| ------------------------ | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **Timestamp 단위**       | epoch milliseconds (`Date.now()`)                                                                                                                                                                     |
| **서명 페이로드 형식**   | `{timestamp}.{method}.{URI}` — URI는 **path만** 포함, query string 미포함. 예: `1717843200000.GET./ncc/campaigns`                                                                                     |
| **서명 알고리즘**        | HMAC-SHA256, key = `SECRET_KEY`, output = Base64 인코딩                                                                                                                                               |
| **Clock skew tolerance** | 서버 측 ±5분 가량. 시스템 시각 동기화(NTP) 필수                                                                                                                                                       |
| **헤더 매핑**            | `X-API-KEY` = `ACCESS_LICENSE` 값, `X-Customer` = `CUSTOMER_ID` 값, `X-Timestamp` = epoch ms, `X-Signature` = HMAC-SHA256 서명. **`SECRET_KEY`는 서명 생성에만 사용되며 HTTP 헤더로 전송하지 않는다** |
| **재시도 의미론**        | `401` → timestamp 재생성 후 서명 재시도 1회 (clock skew 대응), `5xx` → exponential backoff (최대 3회, 기본 간격 1s), `429` → `Retry-After` 헤더 값 존중 후 재시도                                     |

- Base URL: `https://api.searchad.naver.com`
- 공통 GET/POST/PUT 래퍼 + 에러 핸들링 (자격증명 미노출)
- verbose logging 모드: 요청 헤더 구조·응답 상태 로깅 (자격증명 값 제외) [R-7]

**`src/cli.ts`**

- `npm start` → 자격증명 검증 → `/ncc/bizmoney` GET → 잔액 출력
- 성공: `"[OK] 네이버 광고 계정 연결 성공. 비즈머니 잔액: ₩XX,XXX"`
- 실패: `"[ERROR] 인증 실패. NAVER_ADS_ACCESS_LICENSE 값을 확인하세요."` (값 미노출)

### Fixture-capture 절차 [R-4]

1. API 키 발급 완료 후, 실 API에 read 요청 1건 실행
2. 해당 요청의 입력 파라미터(timestamp, method, URI)와 생성된 HMAC 서명, 요청 헤더를 기록
3. `tests/fixtures/hmac-signature.json`에 저장 (자격증명 값은 마스킹, 서명 입출력만 보존)
4. 이후 단위 테스트에서 동일 입력에 대해 결정론적 서명 재현을 검증
5. **주의**: 이 fixture 파일에 `SECRET_KEY` 원문이 포함되지 않도록 `[검증자]`가 확인

| **Decision**                | Naver Search Ad API (공식 REST API)를 통한 인증 및 데이터 접근, 로컬 CLI를 primary 배포 타겟으로 채택                                                                                                                                                                                                    |
| **Drivers**                 | (1) ToS 준수 필수 (P2), (2) 봇 탐지 회피 불가 (D2), (3) 자격증명 안전성 (P1), (4) 장기 유지보수 비용                                                                                                                                                                                                     |
| **Alternatives considered** | (A) Playwright 웹 자동화 — ToS 회색지대·봇 탐지·유지보수 부담으로 2순위, (B) Naver OAuth — 용도 불일치로 배제, (C) Hybrid (SA API + Web) — Q5 답변에 따라 Phase 2에서 검토 가능                                                                                                                          |
| **Why chosen**              | 공식 API가 존재하고 무료이며, 요구사항(계정 접근·데이터 조회)을 충족. ID/PW 대비 보안 우수 (HMAC 서명). 봇 탐지 문제 원천 없음                                                                                                                                                                           |
| **Consequences**            | 사용자가 API 키 3종을 추가 발급해야 함 (1회성 작업, ~5분). `.env` 키 이름 변경 필요. **Option A는 P4(그린필드 단순성)를 의식적으로 양보한다 — API 키 3종 발급이라는 사용자 측 blocking dependency를 부과하지만, P2(ToS 준수)와 P5(점진적 위험)의 가치가 P4 양보를 정당화한다 (~5분 1회성 작업).** [R-11] |
| **Follow-ups**              | (1) 사용자에게 API 키 발급 절차 안내, (2) Q1·Q5 해소 후 구현 범위 확정, (3) Q5에서 SA 외 상품 필요 시 Hybrid 경로 재검토, (4) 다중 CUSTOMER_ID 필요 시 config 확장                                                                                                                                       |
